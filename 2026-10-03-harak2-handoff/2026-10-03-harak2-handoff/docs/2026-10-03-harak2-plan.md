## 1. كيف تُقرأ هذه الخطة

- **المرحلة 0 (التجربة التقنية) مفصّلة بالكامل** لأنها تبدأ فورًا.
- **المرحلة 1 مفصّلة بالمهام.**
- **المراحل 2–8 مفصّلة على مستوى المهام الرئيسية فقط**، وتُفصَّل كل منها قبل بدئها. السبب: نتائج التجربة التقنية قد تغيّر تصميم التحرير والبيانات، وتفصيل كل شيء الآن يعطي دقة زائفة.
- **التقدير الزمني:** لا أقدّم أيامًا أو أسابيع. كل مرحلة لها حجم نسبي (صغير / متوسط / كبير / كبير جدًا). التقدير الزمني يُبنى بعد المرحلة 0 على سرعة الفريق الفعلية.

## 2. قواعد العمل (تنطبق على كل المهام)

1. **الاختبار أولًا:** كل مهمة تبدأ باختبار فاشل، ثم كود يُنجحه، ثم تحسين.
2. **مهمة صغيرة = تعديل واحد مستقل** يُحفظ في git برسالة واضحة.
3. **لا تُغلق مهمة** قبل نجاح كل الاختبارات الآلية في CI.
4. **أي انحراف عن المواصفة** يوقف العمل ويُعرض على المالك، ثم تُحدَّث المواصفة قبل الاستمرار.
5. **حراك 1 لا يُعدَّل أبدًا.** يُستخدم للقراءة والتشغيل في اختبارات التطابق فقط.
6. **إصدارات الأدوات:** أحدث إصدار مستقر يُتحقق منه عند بدء كل مرحلة، ويُثبَّت في ملفات الاعتماديات.

## 3. هيكل المستودع

```
harak2/
├── backend/        # Django REST + Celery (Python)
├── frontend/       # React + Vite + TipTap
├── collab/         # Hocuspocus / Yjs (Node)
├── shared/         # مخطط مستند Yjs ومحوّله (مشترك بين collab و frontend)
├── infra/          # Docker Compose, Keycloak للاختبار, إعدادات CI
├── evals/          # المجموعة الذهبية وأداة تقييم الذكاء الاصطناعي
├── parity/         # تشغيل حراك 1 آليًا لاختبارات التطابق
├── spike/          # المرحلة 0 — تجريبي يُرمى، لا يُستورد منه شيء
└── docs/           # المواصفة، الخطة، سجل القرارات
```

## 4. المراحل

### المرحلة 0 — التجربة التقنية للتحرير المتزامن (حجم: صغير–متوسط)

**الهدف:** حسم الأسئلة الثلاثة في القسم 9 من المواصفة قبل بناء أي شيء.
**الكود تجريبي يُرمى** ويبقى داخل `spike/` فقط.

| # | المهمة | الاختبار / معيار الإنجاز |
|---|---|---|
| 0.1 | إنشاء `spike/` بتطبيق Vite + React + TipTap مع امتداد التعاون، وخادم Hocuspocus محلي | محرران في نافذتين يتزامنان |
| 0.2 | تعريف مخطط مستند Yjs: `Y.Map` للعقد (node_key → {parent, level, order, deleted})، و`Y.Map` للكتل (block_key → {node_key, type, deleted, content: Y.XmlFragment}) | اختبار وحدة ينشئ شجرة من 3 مستويات وكتلًا من كل نوع |
| 0.3 | دالة `materialize(doc) → rows` ودالة عكسية `hydrate(rows) → doc` | اختبار ذهاب وإياب على مستند ثابت بنصوص عربية وإنجليزية ومختلطة: لا فقد |
| 0.4 | اختبار عشوائي (property-based) للذهاب والإياب | 1000 مستند عشوائي بنصوص عربية: لا فقد |
| 0.5 | محاكاة 3–5 عملاء Yjs بعمليات متزامنة عشوائية (إدراج، حذف، نقل عقدة، حذف ناعم) ثم مزامنة | كل العملاء يتقاربون لنفس الحالة، والتحويل إلى صفوف متطابق |
| 0.6 | تثبيت الملاحظات بـ `Y.RelativePosition` | بعد إدراجات وحذوفات متزامنة قبل الموضع وبعده، يبقى النص المقتبس هو نفسه؛ وعند حذف موضعه تُكتشف الحالة |
| 0.7 | فحص العربية RTL في TipTap: فقرات، قوائم، نص مختلط، أرقام، علامات ترقيم، نسخ ولصق من Word | قائمة فحص يدوية + لقطات شاشة آلية (Playwright) بالعربية |
| 0.8 | تقرير النتائج وقرار البوابة | تقرير مكتوب في `docs/` |

**بوابة القرار بعد 0.8 (يقررها المالك):**
- **نجاح الأسئلة الثلاثة:** المتابعة بالتصميم كما هو، ونقل مخطط المستند المعتمد إلى `shared/` ككود إنتاجي جديد (وليس نسخًا من `spike/`).
- **فشل أي منها:** العودة إلى القفل المرن، وتحديث المواصفة قبل المرحلة 1.

### المرحلة 1 — الأساس (حجم: متوسط)

**الهدف:** هيكل يعمل من البداية للنهاية، مع الفصل بين المؤسسات والهوية الأساسية.

| # | المهمة | الاختبار / معيار الإنجاز |
|---|---|---|
| 1.1 | Docker Compose: PostgreSQL، Redis، backend، worker (Celery)، beat، frontend، collab | `docker compose up` يشغّل كل الخدمات، وفحص الصحة لكل خدمة ينجح |
| 1.2 | CI: تشغيل اختبارات backend وfrontend وcollab مع كل تعديل | فشل أي اختبار يمنع الدمج |
| 1.3 | مشروع Django + DRF، إعدادات حسب البيئة، سجلات منظمة، Sentry | اختبار دخان لنقطة الصحة |
| 1.4 | نماذج Organization وUser وMembership والأدوار (بما فيها pending) | اختبارات الإنشاء والقيود |
| 1.5 | **طبقة الفصل المركزية:** مدير استعلامات يفرض `organization_id` من سياق الطلب، ويرفض أي استعلام بلا سياق | اختبار: استعلام بلا سياق مؤسسة يرمي خطأ |
| 1.6 | **أداة اختبار الفصل الآلية:** تمر على كل المسارات المسجلة، وتحاول الوصول لكائن من مؤسسة أخرى | أي مسار جديد بلا تغطية يُفشل الاختبار تلقائيًا |
| 1.7 | تسجيل الدخول بكلمة المرور، وتبديل سياق المؤسسة للمستخدم متعدد العضويات | اختبارات الدخول والخروج وتبديل السياق |
| 1.8 | سجل التدقيق (إضافة فقط) ونقطة كتابة واحدة له | اختبار: التعديل أو الحذف على السجل مرفوض |
| 1.9 | الواجهة: هيكل React ثنائي اللغة والاتجاه، صفحة دخول، تبديل المؤسسة | اختبار Playwright للدخول بالعربية والإنجليزية |

**معيار إنجاز المرحلة:** مستخدمان في مؤسستين مختلفتين يدخلان، ولا يرى أي منهما شيئًا من بيانات الآخر، مع نجاح أداة اختبار الفصل.

### المرحلة 2 — نواة المحتوى (حجم: كبير)

**الهدف:** الكفايات، والهياكل، والبرامج، والنسخ تعمل عبر الواجهة البرمجية والواجهة.

- **2.1** إطار الكفايات بنسخ: إنشاء، نشر، نسخة جديدة عند تعديل المنشور.
- **2.2** استيراد الكفايات من Excel/CSV مع معاينة وكشف أخطاء الصفوف قبل الحفظ.
- **2.3** قوالب الهيكل بنسخ: مستويات بالعربية والإنجليزية، حد أقصى 5.
- **2.4** Program وProgramCollaborator وProgramVersion، وقاعدة «النسخة المقفلة غير قابلة للتعديل» في طبقة النموذج.
- **2.5** Node وBlock بمفاتيح ثابتة، وحذف ناعم، ونسخ الصفوف عند إنشاء نسخة جديدة.
- **2.6** AlignmentLink (هدف ↔ كفاية، تقويم ↔ هدف، هدف ↔ هدف أعلى).
- **2.7** مقارنة نسختين على مستوى الكتل بالمفتاح الثابت.
- **2.8** الواجهة: إدارة الكفايات والقوالب، شجرة البرنامج حسب القالب، عرض المقارنة.

**معيار الإنجاز:** إنشاء برنامج بقالب من 4 مستويات، ونسختين منه، ومقارنة صحيحة بينهما.

### المرحلة 3 — التحرير المتزامن الإنتاجي (حجم: كبير)

**الهدف:** تحويل نتائج المرحلة 0 إلى خدمة إنتاجية.

- **3.1** مخطط المستند والمحوّل في `shared/` (كتابة جديدة بناء على نتائج المرحلة 0، مع نقل اختباراتها).
- **3.2** خدمة `collab/`: مصادقة برمز قصير العمر خاص بمستند واحد يصدره Django.
- **3.3** حفظ حالة المستند (DraftDocument) والتحويل الدوري وعند الإرسال إلى صفوف عبر نقطة في Django.
- **3.4** رفض التعديل على أي نسخة ليست مسودة.
- **3.5** الحضور الحي (مؤشرات، من يحرر أي كتلة).
- **3.6** الملاحظات بمواقع نسبية، وقسم «ملاحظات بلا موضع».
- **3.7** سلوك التعطل: قراءة فقط مع تنبيه، ثم إعادة اتصال ودمج.
- **3.8** فشل التحويل: الاحتفاظ بآخر صفوف سليمة ومنع الإرسال برسالة واضحة.

**معيار الإنجاز:** اختبارات القسم 8.1 البند 5 من المواصفة تنجح على الخدمة الإنتاجية.

### المرحلة 4 — محرك الجودة (حجم: كبير جدًا)

**الهدف:** تقرير الجودة الهجين ووكلاؤه الأربعة، مع بوابة دقة.

- **4.1** `parity/`: تشغيل حراك 1 في متصفح آلي على مجموعة نصوص ثابتة واستخراج نتائجه، دون أي تعديل على كوده.
- **4.2** نقل قواعد حراك إلى Python، قاعدة قاعدة، مع اختبار تطابق لكل قاعدة.
- **4.3** QualityReport وFinding والتجميع صعودًا على الشجرة، والتجاهل بسبب.
- **4.4** بوابة الذكاء الاصطناعي: مزوّد قابل للتبديل، تحقق من صيغة JSON، إعادة محاولة بفواصل متزايدة، تخزين مؤقت ببصمة المحتوى، سجل AIUsage، حصة شهرية، ووضع «قواعد فقط».
- **4.5** `evals/`: أداة إدخال المجموعة الذهبية، وحساب اتفاق الخبراء، وحساب مقاييس كل وكيل.
- **4.6–4.9** الوكلاء الأربعة (التصنيف، المواءمة، الصياغة، الاستيراد)، كل واحد مع:
  - ردود مسجلة لاختبارات CI.
  - اختبارات حقن انقطاع المهلة والصيغة الخاطئة وحقن التعليمات.
  - تشغيل على المجموعة الذهبية.
- **4.10** الواجهة: لوحة التقرير بجانب المحرر، وعرض الخلاف بين القاعدة والذكاء الاصطناعي.

**معيار الإنجاز:** تطابق كامل مع حراك 1، وكل وكيل يتجاوز حد الدقة الذي يحدده المالك.
**مهمة غير برمجية موازية:** بناء المجموعة الذهبية بخبراء تخصص (المالك وزملاء). تبدأ مع المرحلة 2 لأنها تستغرق وقتًا.
