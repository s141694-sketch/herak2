## 1. الهدف والسياق

### 1.1 نوع المشروع
منتج ريادي حقيقي للسوق (وليس تسليمًا أكاديميًا). المنصة عامة على المدى البعيد، لكن النسخة الأولى تُبنى لشريحة واحدة.

### 1.2 العميل الأول
مراكز التدريب ووحدات التدريب في الشركات.

### 1.3 الآلام التي تحلها النسخة الأولى
1. ضعف جودة المحتوى التدريبي ومواءمته مع الكفايات المطلوبة للأدوار الوظيفية.
2. بطء اعتماد المحتوى وتشتت الملاحظات (بريد، ورق، رسائل).
3. بطء إنتاج المحتوى التدريبي نفسه.

هذه الآلام الثلاثة مراحل في دورة واحدة: **إنتاج ← فحص الجودة والمواءمة ← اعتماد ← نشر**. ميزة المنتج هي ربط الدورة كاملة.

### 1.4 التموضع
حراك 2 منصة **دورة حياة المحتوى التدريبي** تسبق نظام إدارة التعلم (LMS) وتُصدِّر إليه. لا تنافس أنظمة إدارة التعلم في تقديم الدورات أو تسجيل المتدربين.

### 1.5 مقاربة النطاق المعتمدة
**(أ) شريحة رفيعة عبر الدورة كاملة:** كل محطة بأبسط شكل مفيد، مع إضافتين معتمدتين ترفعان الحجم: التحرير الجماعي المتزامن، والدخول الموحد (OIDC).

### 1.6 مقاييس النجاح
- عدد جولات المراجعة لكل برنامج.
- الزمن من أول مسودة حتى الاعتماد.

يُقاس خط الأساس عند العميل التجريبي قبل الاستخدام، ثم بعده. لا توجد أرقام مستهدفة قبل قياس خط الأساس.

## 2. النطاق ورحلة المستخدم

### 2.1 الأدوار (على مستوى المؤسسة)
| الدور | المسؤولية |
|---|---|
| مدير التدريب (admin) | تهيئة المساحة، المستخدمين، القوالب، الدخول الموحد |
| المؤلف (author) | كتابة المحتوى — غالبًا خبير تخصص وليس مصممًا تعليميًا |
| المراجع (reviewer) | فحص المحتوى وكتابة الملاحظات |
| المعتمِد (approver) | القرار النهائي |
| بانتظار التعيين (pending) | مستخدم دخل عبر SSO ولم يُمنح دورًا؛ بلا أي صلاحية |

إضافة إلى الدور، التحرير في برنامج معيّن يتطلب أن يكون المستخدم ضمن **المشاركين** في ذلك البرنامج (ProgramCollaborator).

### 2.2 الرحلة (خمس محطات)
1. **التهيئة (مرة واحدة):** المدير يرفع إطار الكفايات (Excel/CSV) أو يدخله يدويًا، ويعرّف قوالب الهيكل (حتى 5 مستويات)، وقالب مسار الاعتماد (مراحل متتابعة، مسؤول ومهلة لكل مرحلة)، ويضبط الدخول الموحد إن رغب.
2. **الإنتاج:** المؤلف يبدأ برفع مادة موجودة (PDF/Word) أو بنموذج موجَّه: يختار الكفايات المستهدفة، فيقترح الذكاء الاصطناعي أهدافًا وهيكلًا مبدئيًا يعدّله. التحرير متزامن بين المشاركين. عناصر الاكتمال (من حراك 1): الأهداف، المحتوى، الأنشطة، التقويم، المراجع.
3. **فحص الجودة قبل الإرسال:** تقرير آلي يشمل مستوى بلوم لكل هدف، ومصفوفة المواءمة (كفاية ↔ هدف ↔ تقويم)، وقائمة الاكتمال. كل تنبيه مصحوب بسببه.
4. **الاعتماد:** المراجع يرى المحتوى والتقرير جنبًا إلى جنب، ويكتب ملاحظات مثبتة تتحول إلى مهام. يعيد أو يمرر. عند الاعتماد النهائي تُجمَّد النسخة.
5. **النشر:** تصدير Word وPDF بهوية المؤسسة.

### 2.3 خارج النسخة الأولى (مؤجل عمدًا)
- تصدير SCORM والربط المباشر مع أنظمة إدارة التعلم.
- المسارات المتوازية في الاعتماد، وغرفة الإجماع، والاعتماد عبر رابط سحري بلا تسجيل دخول.
- الواتساب، ولوحات التحليل للقيادات، وخريطة المنهج.
- منشئ أتمتة بدون برمجة («إذا حدث كذا فافعل كذا»).
- SAML 2.0، والمزامنة التلقائية للمستخدمين (SCIM)، وأمان صفوف قاعدة البيانات (RLS).
- العمل دون اتصال، والعطل الرسمية في حساب المهل.
- تحويل الصوت إلى محتوى، وفحص الملفات من البرمجيات الخبيثة.
- صلاحيات على مستوى القسم.

### 2.4 قائمة المشكلات الإضافية (مرشحة لمراحل لاحقة — فرضيات تحتاج تحققًا من العملاء)
1. تقادم المحتوى: تاريخ صلاحية، تذكير بالمراجعة، تحليل أثر تغيّر الإجراءات.
2. ضياع خبرة المختصين: تحويل مقابلة صوتية إلى مسودة وحدة.
3. التكرار بين الأقسام: مكتبة وحدات قابلة لإعادة الاستخدام.
4. ضعف أسئلة التقويم: تحليل نتائج المتدربين بعد التطبيق.
5. عبء التدقيق والاعتماد: «حزمة تدقيق» تُولَّد بضغطة.
6. التباين بين المدربين: توليد دليل المدرب آليًا.
7. إثبات العائد للإدارة: لوحة تغطية الكفايات للأدوار الوظيفية.
8. ازدواجية اللغة: مسرد مصطلحات للمؤسسة.

## 3. المعمارية

### 3.1 التقنيات
Django REST Framework + PostgreSQL للخادم، React + Vite للواجهة، Celery + Redis للمهام الخلفية، Node (Hocuspocus) لخدمة التعاون، Docker لتغليف كل الخدمات. الاختيار مبني على خبرة المالك القائمة.

### 3.2 الوحدات
| # | الوحدة | الغرض | تعتمد على |
|---|---|---|---|
| 1 | الواجهة (React + Vite) | واجهة ثنائية اللغة والاتجاه (عربي RTL / إنجليزي LTR)، محرر TipTap | الخادم، خدمة التعاون |
| 2 | الخادم الرئيسي (Django REST) | الحسابات، المؤسسات، البرامج، النسخ، مسارات الاعتماد، الملاحظات، الصلاحيات | PostgreSQL |
| 3 | محرك الجودة | قواعد حراك المنقولة إلى Python + استدعاءات الذكاء الاصطناعي، يعمل في الخلفية | Celery، بوابة الذكاء الاصطناعي |
| 4 | بوابة الذكاء الاصطناعي | نقطة مرور وحيدة لكل الطلبات؛ مزوّد قابل للتبديل؛ تسجيل التكلفة لكل مؤسسة؛ التحقق من صيغة المخرجات | مزوّد خارجي (أو محلي مستقبلًا) |
| 5 | الاستيراد | استخراج النص من PDF/Word واقتراح توزيعه على الشجرة؛ المؤلف يؤكد | بوابة الذكاء الاصطناعي |
| 6 | الإشعارات | داخل المنصة + بريد؛ تذكيرات مجدولة (Celery Beat)؛ خيار ملخص يومي | سجل التدقيق |
| 7 | التصدير | Word عبر python-docx ثم PDF، بهوية المؤسسة؛ مستويات الشجرة ← مستويات العناوين | الصفوف المعتمدة |
| 8 | التخزين | PostgreSQL للبيانات؛ تخزين كائنات متوافق مع S3 للملفات؛ روابط مؤقتة موقّعة | — |
| 9 | خدمة التعاون (Hocuspocus / Yjs) | التحرير المتزامن للمسودات؛ الحضور الحي؛ تحويل المستند الحي إلى صفوف | رمز قصير العمر يصدره Django |

### 3.3 تعدد المؤسسات
قاعدة بيانات مشتركة؛ كل جدول يحمل `organization_id`؛ الفصل يُفرض في **طبقة مركزية واحدة** (وليس في كل استعلام). اختبارات فصل إلزامية (القسم 8).

### 3.4 الاستضافة
سحابي أولًا (خدمة SaaS)، وكل الخدمات مغلّفة بـ Docker حتى يمكن التثبيت لاحقًا على خوادم العميل دون إعادة بناء.

### 3.5 مسار البيانات
المؤلفون يحررون مستند Yjs الحي ← خدمة التعاون تحوّله إلى صفوف (دوريًا وعند الإرسال) ← الخادم ينشئ مهمة تحليل للكتل المتغيرة ← محرك الجودة (قواعد ثم ذكاء اصطناعي) ← التقرير يُخزَّن ويظهر ← الإرسال يبدأ مسار الاعتماد ← إشعارات ← اعتماد ← نسخة مجمّدة ← تصدير.

## 4. نموذج البيانات

### 4.1 المؤسسة والمستخدمون
- **Organization:** الاسم، الهوية البصرية (شعار، ألوان)، الإعدادات (أيام العمل، سلوك فحص ما قبل الإرسال، تفعيل الذكاء الاصطناعي، الحصة الشهرية، مدة الجلسة).
- **User / Membership:** المستخدم يرتبط بمؤسسة أو أكثر عبر عضوية تحدد دوره.
- **VerifiedDomain:** نطاق بريد أثبتت المؤسسة ملكيته عبر سجل DNS TXT.
- **IdentityProviderConfig:** إعدادات OIDC للمؤسسة (issuer، client id، secret مشفّر)، حالة اختبار الاتصال، تفعيل الفرض.

### 4.2 الكفايات
- **CompetencyFramework** (له نسخ) ← **Competency:** رمز، عنوان، وصف، مستوى، كفاية أم اختيارية.
- تعديل إطار منشور ينشئ نسخة جديدة؛ البرامج المعتمدة تبقى على نسختها.

### 4.3 الهيكل والمحتوى
- **StructureTemplate** (له نسخ) ← **Level:** أسماء المستويات بالعربية والإنجليزية بالترتيب؛ حد أقصى 5 مستويات؛ للمؤسسة أكثر من قالب. تعديل قالب مستخدم ينشئ نسخة جديدة منه.
- **Program:** عنوان، دور وظيفي مستهدف، مالك، قالب الهيكل، حالة (`draft` / `in_review` / `approved` / `archived`).
- **ProgramCollaborator:** المستخدمون المشاركون في تحرير البرنامج.
- **ProgramVersion:** رقم، حالة، منشئ، وقت؛ عند الاعتماد: المعتمِد والوقت. النسخة المقفلة أو المعتمدة **غير قابلة للتعديل**، ويُفرض ذلك في طبقة النموذج.
- **DraftDocument:** حالة مستند Yjs للمسودة الحية (مرتبطة بنسخة في حالة مسودة).
- **Node:** عقدة في شجرة النسخة: `node_key` ثابت عبر النسخ، الأب، المستوى، الترتيب، علامة حذف ناعم.
- **Block:** كتلة مرتبطة بعقدة (في أي مستوى): `block_key` ثابت عبر النسخ، النوع (`objective` / `content` / `activity` / `assessment` / `reference`)، المحتوى المنسق (JSON من TipTap)، بصمة المحتوى، علامة حذف ناعم.
- **AlignmentLink:** روابط صريحة: هدف ↔ كفاية، تقويم ↔ هدف، هدف ↔ هدف أعلى (اختياري). يثبّتها المؤلف؛ الذكاء الاصطناعي يقترح فقط.

**القاعدة:** المسودة الحية مستند Yjs؛ النسخ المقفلة والمعتمدة صفوف ثابتة. الكتل والعقد تُنسخ كصفوف لكل نسخة.

### 4.4 الجودة
- **QualityReport:** لكل نسخة؛ الحالة (`running` / `complete` / `partial_rules_only` / `failed`)؛ إصدار القواعد؛ إصدار التعليمات والنموذج.
- **Finding:** النوع، الشدة (`critical` / `warning` / `info`)، العقدة أو الكتلة، التفسير، المصدر (`rule` / `ai`)، الثقة، حالة التجاهل وسببه.

### 4.5 الاعتماد والملاحظات
- **WorkflowTemplate** ← **Stage:** ترتيب، مسؤول (مستخدم أو دور)، مهلة بأيام العمل، سلوك إعادة الإرسال (`same_stage` افتراضيًا / `restart`).
- **WorkflowInstance** ← **StageDecision:** المرحلة، المستخدم، القرار (`approve` / `return`)، الملاحظة، الوقت.
- **Comment:** مرتبط بـ `block_key` أو `node_key`، موقع نسبي من Yjs في المسودة، النص المقتبس، التصنيف (`must_fix` / `suggestion`)، الحالة (`open` / `resolved`)، الردود. الملاحظات المفتوحة تنتقل للنسخة الجديدة؛ إن حُذف موضعها تظهر في قسم «ملاحظات بلا موضع».

### 4.6 البنية المساندة
- **AuditLog:** سجل أحداث للإضافة فقط.
- **File:** الملفات المرفوعة والمصدَّرة.
- **Reminder:** التذكيرات المجدولة.
- **AIUsage:** الاستهلاك لكل مؤسسة ولكل خاصية.

## 5. محرك الجودة والوكلاء

### 5.1 المبادئ
1. القواعد أولًا والذكاء الاصطناعي ثانيًا: قواعد حراك تعمل دائمًا؛ الذكاء الاصطناعي حيث تعجز القواعد فقط.
2. الذكاء الاصطناعي يقترح ولا يقرر، ولا يملك أي صلاحية تنفيذ. كل نتيجة تحمل تفسيرًا وثقة ومصدرًا.
3. مخرجات JSON بصيغة محددة يُتحقق منها؛ الرد غير المطابق يُرفض ولا يظهر للمستخدم.
4. وضع «قواعد فقط» قابل للتفعيل لكل مؤسسة.

### 5.2 مسار التحليل
1. **التشغيل:** خفيف عند التحويل إلى صفوف (الكتل التي تغيّرت بصمتها فقط)؛ كامل عند الإرسال.
2. **طبقة القواعد:** الاكتمال؛ تصنيف بلوم بمطابقة الأفعال؛ وجود الروابط؛ الشرط الإلزامي: كل كفاية مستهدفة تصل إلى تقويم واحد على الأقل في الشجرة.
3. **طبقة الذكاء الاصطناعي** في ثلاث حالات فقط: هدف بلا فعل واضح أو بثقة قواعد منخفضة؛ تحقق معنوي من رابط موجود؛ كفاية غير مغطاة (اقتراح هدف).
4. **الدمج:** النتائج تصبح Findings وتُجمَّع صعودًا على مستويات الشجرة. اختلاف القاعدة والذكاء الاصطناعي في بلوم يُعرض صراحة بثقة منخفضة.

### 5.3 وكلاء النسخة الأولى
| الوكيل | الوظيفة |
|---|---|
| التصنيف | مستوى بلوم للحالات الغامضة |
| المواءمة | صحة الروابط بالمعنى، والكفايات غير المغطاة |
| الصياغة | أهداف وهيكل مبدئي من الكفايات؛ إعادة صياغة الأهداف الضعيفة (قبول أو رفض) — تُطبَّق كتعديل داخل المستند الحي |
| الاستيراد | توزيع نص الملف المرفوع على الشجرة والكتل؛ تأكيد المؤلف إلزامي |

### 5.4 ضبط التكلفة
- تخزين مؤقت ببصمة المحتوى: الكتلة غير المتغيرة لا يُعاد تحليلها.
- حصة شهرية لكل مؤسسة؛ عند انتهائها يعمل المنتج بالقواعد فقط مع تنبيه.

### 5.5 بوابة الإطلاق
لا يُطلق أي وكيل (ولا أي تغيير في تعليماته أو نموذجه) قبل تجاوز حد الدقة الذي يحدده المالك على المجموعة الذهبية (القسم 8.2). حالات رفض المستخدمين لاقتراحات الذكاء الاصطناعي تُسجَّل لقياس الدقة المستمر.

## 6. الموافقات والأتمتة والتحرير المتزامن

### 6.1 دورة حياة النسخة
`draft` ← (فحص ما قبل الإرسال) ← `submitted` ← `in_stage(1..n)` ← `approved` ← `exported`

مسارات جانبية: `returned` (تنشأ نسخة مسودة جديدة منسوخة)، `withdrawn` (من المؤلف قبل أي قرار)، `cancelled` (من المدير).

كل انتقال يمر عبر نقطة واحدة في الكود ويُسجَّل في سجل التدقيق.

### 6.2 قواعد السلوك
1. **فحص ما قبل الإرسال:** الملاحظات الآلية الحرجة إما تمنع الإرسال أو تسمح به بسبب مكتوب يراه المراجع. الافتراضي: السماح بسبب.
2. **ملاحظات المراجع:** `must_fix` تمنع الاعتماد النهائي ما دامت مفتوحة؛ `suggestion` لا تمنع.
3. **الإعادة تتطلب ملاحظة واحدة على الأقل.**
4. **إعادة الإرسال** تعود لنفس المرحلة التي أعادت (افتراضي قابل للتغيير في القالب).
5. **المسؤول عن المرحلة:** شخص، أو دور يستطيع أي حامل له «استلام» المهمة.
6. **القفل:** المحتوى المُرسل مقفل؛ خدمة التعاون ترفض أي تعديل على نسخة ليست مسودة.
7. **من يكتب ويغلق الملاحظات:** كل من له صلاحية على البرنامج يستطيع كتابة ملاحظة والرد عليها. المؤلف يعلّم الملاحظة «محلولة». عند إعادة الإرسال يرى المراجع قائمة بملاحظات `must_fix` التي عُلّمت محلولة، ويستطيع إعادة فتح أي منها. الاعتماد يُمنع فقط بالملاحظات المفتوحة.

### 6.3 المهل والتذكير والتصعيد
- الموعد = دخول المرحلة + المهلة بأيام عمل المؤسسة.
- تذكير قبل الموعد بيوم عمل، ثم عند الموعد، ثم تصعيد للمدير بعد تأخر تحدده المؤسسة (الافتراضي: يوما عمل).

### 6.4 الأتمتة (قواعد ثابتة مدمجة)
| الحدث | ما يحدث تلقائيًا |
|---|---|
| تحويل المسودة إلى صفوف | تحليل الكتل المتغيرة |
| إرسال | تحليل كامل، ثم إشعار المرحلة الأولى |
| قرار المراجع | إشعار المؤلف أو المرحلة التالية |
| تأخر | تذكير، ثم تصعيد |
| اعتماد | تجميد النسخة، توليد Word وPDF، إشعار الجميع |

كل حدث يُكتب في سجل التدقيق أولًا، ومنه تتولد الإشعارات والمهام عبر Celery.

### 6.5 الإشعارات
داخل المنصة وعبر البريد؛ خيار ملخص يومي؛ روابط البريد تتطلب تسجيل الدخول.

### 6.6 التحرير الجماعي المتزامن
- **التقنية:** Yjs (CRDT) + TipTap مع امتداد التعاون، وخادم Hocuspocus (Node).
- **المصادقة:** رمز قصير العمر خاص بمستند واحد يصدره Django بعد التحقق من العضوية والمشاركة.
- **الحضور الحي:** مؤشرات بأسماء وألوان، وإظهار من يحرر أي كتلة.
- **الحذف الناعم** للعقد والكتل لتمكين الاسترجاع عند التعارض.
- **الملاحظات على المسودة** تُثبَّت بمواقع Yjs النسبية.
- **التحويل إلى صفوف:** دوري وعند الإرسال؛ الصفوف هي المرجع للتحليل والنسخ والمقارنة.
- العمل دون اتصال: خارج النسخة الأولى.

## 7. الأمان ومعالجة الأخطاء

### 7.1 الهوية والدخول
- كلمات مرور بالتشفير القياسي في Django.
- التحقق الثنائي (MFA): اختياري للجميع؛ قابل للفرض على المديرين والمعتمِدين؛ يُفوَّض لمزوّد الهوية عند استخدام SSO.

### 7.2 الدخول الموحد (OIDC) — ضمن النسخة الأولى
- **البروتوكول:** OIDC عام لكل مؤسسة (يغطي Microsoft Entra ID وGoogle Workspace ومعظم المزوّدين). SAML 2.0 مؤجل.
- **إثبات ملكية النطاق:** سجل DNS TXT قبل ربط أي نطاق بريد بالمؤسسة.
- **المسار:** البريد ← معرفة النطاق ← التحويل لمزوّد المؤسسة ← العودة مسجَّلًا.
- **الحساب الجديد:** يُنشأ تلقائيًا بحالة «بانتظار التعيين» بلا صلاحيات.
- **الفرض:** يمكن إلغاء كلمات المرور لأعضاء المؤسسة؛ يبقى حساب طوارئ واحد بكلمة مرور وتحقق ثنائي إلزامي.
- **اختبار الاتصال** إلزامي قبل تفعيل الفرض.
- **إلغاء الوصول:** مدة جلسة قصيرة قابلة للضبط لمستخدمي SSO (الافتراضي: 8 ساعات)؛ SCIM مؤجل.
- **المستخدم في أكثر من مؤسسة:** الجلسة تعمل في سياق مؤسسة واحدة في كل مرة.
- **المكتبة:** مكتبة مصادقة ناضجة لـ Django (مثل django-allauth)، مع التحقق من دعمها الحالي لـ OIDC متعدد المؤسسات عند التنفيذ.

### 7.3 الفصل والصلاحيات
- الفصل بين المؤسسات في الطبقة المركزية مع اختبارات إلزامية؛ RLS مؤجل، **ولا يُطلق المنتج لعميل حكومي قبل إضافته**.
- الصلاحيات تُفحص في كل طلب: الدور في المؤسسة، ثم المشاركة في البرنامج.

### 7.4 البيانات
- اتصال مشفّر في كل مكان، وتشفير للبيانات المخزنة.
- الملفات عبر روابط مؤقتة موقّعة.
- نسخ احتياطي يومي، مع تمرين استرجاع دوري.
- أسرار مزوّدي الهوية مخزنة مشفّرة.

### 7.5 الذكاء الاصطناعي
- تقليل البيانات: لا يُرسل إلا الكتل اللازمة.
- الحماية من حقن التعليمات: المحتوى يُعامل كبيانات، والمخرجات يُتحقق من صيغتها، والذكاء الاصطناعي بلا صلاحية تنفيذ.

### 7.6 حماية عامة
تحديد معدل الطلبات لكل مستخدم؛ التحقق من نوع الملفات المرفوعة وحجمها.

### 7.7 معالجة الأخطاء
المبدأ: لا يتعطل العمل الأساسي بسبب عطل في خدمة مساندة.

| العطل | السلوك |
|---|---|
| الذكاء الاصطناعي يتعطل أو تنتهي مهلته | إعادة محاولة بفواصل متزايدة؛ ثم تقرير `partial_rules_only` مع تنبيه؛ الإرسال لا يُمنع |
| فشل مهمة تحليل | الحالة ظاهرة، وزر إعادة المحاولة |
| تعطل خدمة التعاون | المحرر للقراءة فقط مع تنبيه؛ إعادة اتصال ودمج تلقائي |
| فشل التحويل إلى صفوف | تبقى آخر صفوف سليمة؛ تنبيه تقني؛ **يُمنع الإرسال** برسالة واضحة (الحالة الوحيدة المانعة) |
| فشل إرسال البريد | إعادة محاولة؛ الإشعار داخل المنصة هو المصدر المضمون |
| فشل التصدير | إعادة محاولة؛ الاعتماد لا يُلغى |
| فشل قراءة ملف مستورد | بديل يدوي: لصق النص |
| خطأ في إعداد SSO | يكشفه اختبار الاتصال قبل التفعيل |
| تعطل مزوّد الهوية | رسالة واضحة، والإشارة إلى حساب الطوارئ |
| بريد خارج النطاقات المسموحة | رفض مع توضيح السبب |

الرسائل للمستخدم ثنائية اللغة، وتقول ماذا حدث وماذا يفعل الآن.

**المراقبة:** أداة تتبع أخطاء (مثل Sentry)، سجلات منظمة، فحوص صحة لكل خدمة.

## 8. الاختبار

### 8.1 اختبارات آلية (مع كل تعديل في الكود)
1. **تطابق قواعد حراك:** مجموعة نصوص ثابتة على حراك 1 (يُشغَّل في متصفح آلي دون أي تعديل على كوده) وعلى النسخة المنقولة؛ أي اختلاف يُفشل الاختبار.
2. **آلة الحالات:** كل انتقال مسموح وكل انتقال ممنوع.
3. **الفصل بين المؤسسات:** اختبار يمر تلقائيًا على كل نقطة في الواجهة البرمجية، والنقاط الجديدة تدخله تلقائيًا.
4. **خط التحليل:** ردود ذكاء اصطناعي مسجلة؛ حقن انقطاع المهلة، والصيغة الخاطئة، ومحاولات حقن التعليمات.
5. **التحرير المتزامن:** 2–5 عملاء محاكين بمحتوى عربي RTL؛ تقارب المستند، والتحويل ذهابًا وإيابًا دون فقد، وثبات الملاحظات، والانقطاع ثم العودة.
6. **الدخول الموحد:** Keycloak محلي في Docker؛ الدخول الأول، ورفض النطاق غير الموثّق، والفرض، وحساب الطوارئ.
7. **التصدير:** بنية ملفات Word (العناوين تتبع الشجرة، الاتجاه سليم).
8. **رحلات كاملة عبر المتصفح** (Playwright) بالعربية والإنجليزية: تهيئة ← تأليف ← إرسال ← مراجعة ← إعادة ← إعادة إرسال ← اعتماد ← تصدير.

### 8.2 تقييم الذكاء الاصطناعي (مسار مستقل)
- مجموعة ذهبية يصنّفها خبراء يدويًا؛ قياس اتفاق الخبراء أولًا كسقف واقعي.
- المقاييس: دقة تصنيف بلوم؛ دقة وشمول كشف أخطاء المواءمة.
- يعمل عند أي تغيير في التعليمات أو النموذج؛ بوابة إطلاق بحد يحدده المالك.

### 8.3 غير وظيفي وميداني
- اختبار حمل خفيف (عدة محررين على مستند واحد؛ طابور التحليل تحت ضغط).
- تمرين استرجاع النسخ الاحتياطية.
- قبول العميل التجريبي: قياس قبل وبعد (القسم 1.6) + جلسات استخدام مع خبراء التخصص.

## 9. ترتيب البدء: التجربة التقنية (Spike)

أول مهمة في خطة التنفيذ، وكودها **تجريبي يُرمى** ولا يُبنى عليه مباشرة.

**الأسئلة التي يجب أن تحسمها:**
1. هل يعمل TipTap جيدًا مع العربية والكتابة RTL (بما فيها النص المختلط عربي/إنجليزي)؟
2. هل التحويل من مستند Yjs (شجرة + كتل) إلى صفوف ثم العودة يتم دون فقد للمحتوى؟
3. هل تثبيت الملاحظات بمواقع Yjs النسبية يصمد أمام التعديلات المتزامنة؟

**معيار النجاح:** نجاح الأسئلة الثلاثة في اختبار آلي متكرر. **عند الفشل:** العودة إلى القفل المرن (محرر واحد في كل مرة) قبل بناء بقية النظام، وتحديث هذه المواصفة.
